Solution explanation:
You can drop the argument from your call and that will remove the limitation. The argument is used to tell the qiskit transpiler that you're targeting a specific backend and it will map your circuit given the constraints expressed in that backend's (https://docs.quantum.ibm.com/api/qiskit/qiskit.transpiler.Target). The primary (but not only) constraints the transpiler is concerned with are connectivity and the supported instructions/gates. In the case of selecting an ideal Aer simulator (via ) without any noise there are no connectivity constraints, just the limit in the number of qubits, and the work of the transpiler is solely a function of translating the input circuit's gates to match the basis gates; which for Aer is a much larger superset than . However, by setting as an argument in addition to backend you're overriding that and the transpiler will be ignoring 's basis gates. So you can safely remove the argument in this case. It is important to mention here that this isn't a general solution, as for real backends or potentially other simulators this will result in an invalid transpiler output for a given backend. But in the case of using aer like this without a noise model it should work fine. Also, the model the backend's use support more involved instruction models like heterogeneous gates on different qubits so this solution is really only applicable to a bare without any options set. As an aside the number of qubits limit set on the aer backend should be dynamically set based on the chosen simulation method and the amount of available memory on your system. 24 seems awfully low as a limit though because for a statevector simulation that is ~268 MB of memory and a 25 qubit simulation would require ~537 MB of memory.
