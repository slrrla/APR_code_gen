# non-visual p 케이스 테스트

`non-visual_cases_161_(pass-pass).xlsx`에서 C열 값을 공백 제거·소문자 변환했을 때 `p`인 **86개 행**을 선택했습니다. A열의 SE/SO 구분을 그대로 유지하고, H열에 나열된 Qiskit 버전에서 각각 `buggy.py`와 `fixed.py`를 실행합니다. I열 설명은 원 질문과 소스를 함께 검토하는 참고 자료로 사용했습니다.

각 케이스 폴더에 독립 실행 가능한 `test.py` **85개를 새로 작성**했고, 기존 `issue_018_so/test.py`는 그대로 보존했습니다. 원본 스프레드시트와 `buggy.py`·`fixed.py`는 수정하지 않았습니다.

## 최종 검증 결과

워크북에 지정된 버전 조합 **293개**에서 두 소스를 각각 실행한 최종 결과 **586건**을 기록했습니다. 모든 결과는 현재 테스트·소스 해시와 일치하며, 86개 테스트 모두 구문 검사를 통과했습니다.

| 항목 | 결과 |
| --- | --- |
| 적어도 한 대상 버전에서 buggy 실패 / fixed 통과 | **75개 케이스** |
| assertion FAIL / fixed PASS로 구분 | 70개 케이스, 240개 버전 조합 |
| 예외 ERROR / fixed PASS로 구분 | 5개 케이스(`117`, `377`, `551`, `814`, `870`), 15개 버전 조합 |
| 지정된 모든 버전에서 구분 성공 | 71개 케이스 |
| 일부 버전에서만 구분 성공 | 4개: `334`, `364`, `892`, `1009` |
| 모든 지정 버전에서 구분되지 않아 검토 필요 | **11개**: `015`, `018_so`, `058_so`, `125`, `133`, `163`, `165`, `408`, `425`, `472`, `1033` |
| 버전 조합별 결과 | 구분 성공 255 / 양쪽 PASS 27 / 양쪽 거부 11 |
| fixed 실행 상태 | PASS 282 / FAIL 11 |
| buggy 실행 상태 | FAIL 249 / ERROR 17 / PASS 27 |

fixed의 11회 실패는 `015` 2회, `163` 2회, `472` 6회, `892`의 0.25.0 실행 1회입니다. 최종 행렬에 SKIP, TIMEOUT, 실행 환경 오류, fixed ERROR는 없습니다. 이 집계는 단순 실행 종료 코드 대신 테스트 assertion과 실제 결과를 기준으로 하며, 각 그룹의 별도 pilot·재실행 횟수는 포함하지 않습니다.

원본 소스 172개와 워크북의 SHA256이 선정 시점과 같고, 기존 `018_so` 테스트도 바이트 단위로 보존됨을 확인했습니다.

2026-10-26 재확인에서 `814`의 subTest 밖 assertion이 원래 KeyError 뒤에 부수적인 UnboundLocalError를 만드는 테스트 오류를 수정하고 두 버전에서 양쪽 소스를 재실행했습니다. 최종 결과는 buggy의 실제 `KeyError: '011'` / fixed PASS로 유지됩니다. 위 75개는 검증한 버전과 입력 조건에서의 결과입니다. 특히 `551`은 실제 Aer의 20큐빗 제한을 설정한 조건, `814`는 누락 키가 있는 count 사전 입력에서 검증합니다. `870`의 로컬 pulse 실패가 원문 하드웨어 오류와 내부 원인까지 같다는 뜻은 아닙니다.

## 테스트 방식

- 기존 방식과 같은 `unittest.TestCase` 및 main guard를 사용합니다.
- `MUT` 환경변수로 검사할 소스의 경로를 지정하며, 기본값은 테스트 옆의 `fixed.py`입니다. `runpy.run_path`로 해당 소스를 실제 실행합니다.
- 원 질문의 의도에 따라 구체적인 상태벡터·확률·전체 연산자·회로 구조·실제 실행 결과를 검증합니다. 필요한 경우 모든 기저 입력을 확인하여 우연히 맞는 초기 상태가 결함을 가리지 않도록 했습니다.
- 샷 수의 임의 결과를 정답으로 고정하지 않습니다. 시뮬레이터 seed, 결정적인 물리적 성질, 실제 결과의 집계 관계를 사용합니다.
- `029_so`와 `093`의 설치 예제는 subprocess 호출을 mock하여 명령 구성만 검사합니다. pip 설치, git clone, 셸 명령, 네트워크 접속은 실행하지 않으며 실제 설치 성공을 주장하지 않습니다.

`fixed`가 PASS이고 `buggy`가 FAIL 또는 ERROR일 때 해당 버전에서 구분에 성공한 것으로 기록합니다. 잘못된 human fix를 통과시키거나 정상 동작하는 기존 코드를 실패시키기 위해 검증 조건을 바꾸지 않았습니다.

## 근거 파일

- `selection.json`: 선택한 86개 행, 원본 셀 위치, SE/SO 이름, 대상 버전, 소스 및 워크북 SHA256.
- `environments.json`: 실제 실행 인터프리터와 Qiskit·Terra·Aer·NumPy·SciPy 버전.
- `results.json`: 각 케이스·버전·소스별 실행 상태, 종료 코드, 테스트 수, 해시와 로그 경로.
- `logs/`: 실제 stdout/stderr. 그룹 폴더의 별도 pilot 로그와 구분됩니다.
- `version_results.csv`: 버전별 buggy/fixed 결과와 구분 성공 여부.
- `summary.csv`, `summary.json`: 케이스별 요약과 최종 집계.
- `audit.json`: 테스트 구문, 실행 해시, 원본 소스·워크북 및 기존 `018_so` 테스트 보존 여부 확인.

`version_results.csv`, 요약 및 audit 파일은 전체 실행 뒤 `report` 명령으로 생성했습니다. 해당 명령은 누락된 실행, 오래된 테스트 해시, 원본 소스 변경을 검사하고 문제가 있으면 보고서 생성을 거부합니다.

## 다시 실행하기

PowerShell에서 다음 명령을 사용합니다. `--resume`은 소스·테스트 해시가 같은 기존 결과를 유지하며 누락되거나 변경된 실행을 처리합니다.

```powershell
$batch = 'C:/personal_webpage/my-portfolio/APR_code_gen/Part2_Create_test/reconstructed_cases/nonvisual_p86_20261025'
python "$batch/manage.py" run --resume --workers 4 --timeout 120
python "$batch/manage.py" report
```

특정 케이스를 강제로 다시 실행하려면 `--resume` 없이 범위를 지정합니다.

```powershell
python "$batch/manage.py" run --cases issue_1009 --versions 0.25.0 0.46.3
python "$batch/manage.py" report
```

환경 경로는 `Part1_Create_code/envs/qiskit_0_25_0/python.exe`처럼 **버전 구분에 밑줄**을 사용합니다. 대상 환경은 `qiskit_0_25_0`, `qiskit_0_46_3`, `qiskit_1_0_0`, `qiskit_1_2_4`, `qiskit_2_0_0`, `qiskit_2_5_0`이며, 각 케이스에는 워크북에 명시된 버전만 적용합니다.

실행마다 별도 작업 폴더와 HOME을 사용하고 과학 계산 라이브러리의 스레드 수를 제한합니다. 구형 SciPy가 자신의 DLL 폴더로 이동하는 과정은 샌드박스에서 차단될 수 있습니다. 이는 테스트 assertion 실패와 구분해야 하며, 기존 검증에서는 승인된 로컬 실행으로 확인했습니다. 공유 환경의 패키지를 설치하거나 변경하지 않았습니다.
