# Qiskit APR: 30-case experiment guide

This directory contains the code, generated repairs, evaluation results, and audit evidence for 30 Qiskit `p` cases. Start with the CSV files below; inspect `runs/<run>/tasks/<case>/patched.py` to see a generated repair.

Existing case-specific tests are the evaluator. Each case was evaluated on one pinned Qiskit version: 0.25.3 for 6 cases, 0.46.3 for 12, and 2.5.0 for 12. These results cover those selections, not every case/version combination.

The detailed reports retain their original language. This README is the English operating guide.

| CSV field | Meaning |
|---|---|
| `buggy` | Test result for the original buggy program. |
| `fix` | Test result for the existing reference `fixed.py`. The repair agent did not generate this file. |
| `generated fix` | Test result for the candidate generated by the repair process. |
| `baseline_valid` | The buggy program fails with tests actually executed, while the reference passes. Present in adapter summaries. |
| `repaired` | Valid baseline, present and changed candidate, passing tests, valid syntax, and no suspicious patch flag. |
| `submitted` | The Claude agent ended with the submission sentinel. |
| `strict_success` | Both `repaired` and `submitted` are true. |
| `steps` / `cost_usd` | Recorded agent API calls / token-usage cost for that case. Cost uses the experiment's recorded rates; it is not an invoice. |

`PASS` requires executed, non-skipped tests and a successful unittest result. `FAIL` denotes an assertion failure; `ERROR` denotes another execution failure. `INVALID_RUN` means a successful exit did not establish a valid test run. A test pass establishes correctness only against the existing tests.

### Execution tools

| Tool | What it does |
|---|---|
| `tools/adapter.py` | Selects/prepares exactly 30 cases, pins interpreters, checks source/test hashes, runs tests with `MUT`, snapshots candidates, and exports results. Commands: `prepare`, `baseline`, `validate`. It does not call a repair model. |
| `tools/claude_p30.py` | Runs both native Claude models through the actual `DefaultAgent`, using a file-queue broker. Reads `upstream/configs/apr.yaml`; currently hardcodes the two completed run folders. |

| `tools/claude_api_broker.py` | Separate credential-holding network process. Accepts queued requests for the two experiment model IDs and stores responses; it does not execute generated programs. |

| `tools/claude_finish.py` | One-time historical finalization/recovery after an agent deleted its target. Rewrites validation receipts, manifests, results, and reports; it is not a general rerun command. |
| `tools/pilot_actions.py` | Recorded Codex reproduction/edit/rerun actions for ten cases. Its `patch` stage applies hardcoded recorded edits; it is not an autonomous API repair agent. |

## Local setup for the commands below

These examples use Windows PowerShell and the existing installation on this computer. They do not install or upgrade packages.

```powershell
$AprRoot = 'C:\personal_webpage\my-portfolio\APR_code_gen\Part2_Create_test\reconstructed_cases\apr_p30'

$env:PYTHONPATH = (Join-Path $AprRoot 'tools') + ';' + $Libraries
$env:PYTHONDONTWRITEBYTECODE = '1'
$env:MSWEA_GLOBAL_CONFIG_DIR = Join-Path $AprRoot 'records\runtime_config'
$env:MSWEA_SILENT_STARTUP = '1'
```

Use the pinned Python executable above rather than the original ZIP's `.venv\Scripts\python.exe` launcher. Tests and the Claude driver need the existing mini-swe-agent 2.4.6, Jinja2, PyYAML, and Pydantic packages. Environment tests need Git Bash at `C:\Program Files\Git\bin\bash.exe`.

The adapter and auditor use the standard library. Full auditing additionally needs the original case files and mini-swe-agent source referenced by the manifests. Validation needs the three original Qiskit interpreters referenced there. `support/` supplements those environments; it does not replace them. This directory is tied to recorded local paths rather than being a self-contained portable environment.

## Audit the saved Claude experiment

After the setup block, run:

```powershell
& $Python -B -X utf8 .\tools\audit_claude_runs.py --root $AprRoot
```

This reads archived API records and saved runs, prints a compact JSON result, and makes no API calls or executions of generated programs. It reads original files outside `apr_p30` only for hash checks. Expected saved-artifact result: `passed: true`, zero errors, and four warnings covering two documented validation corrections and two benign blocked-command false positives.

Exit codes: `0` = passed, `1` = audit findings contain errors, `2` = incomplete or unreadable evidence. Leave off `--write` to preserve historical audits. `--write` replaces per-run `final_audit.json` and `records/claude_p30_final_audit.json`. `--capture-probes` writes preparation metadata and is intended for the preparation stage.

## Revalidate existing generated code

Validation writes new logs, probes, snapshots, diffs, and results. Copy a saved run first so historical evidence and timestamps remain intact:

```powershell
$SourceRun = Join-Path $AprRoot 'runs\sonnet5.5p30'
$ValidationRun = Join-Path $AprRoot 'records\revalidation\sonnet_review_01'
if (Test-Path -LiteralPath $ValidationRun) { throw 'Choose a fresh validation directory.' }
New-Item -ItemType Directory -Path (Split-Path -Parent $ValidationRun) -Force | Out-Null
Copy-Item -LiteralPath $SourceRun -Destination $ValidationRun -Recurse

# Evaluate one case first.
& $Python -B -X utf8 .\tools\adapter.py validate --run-dir $ValidationRun --cases issue_036 --workers 1 --timeout 120

# Evaluate all 30 copied candidates.
& $Python -B -X utf8 .\tools\adapter.py validate --run-dir $ValidationRun --workers 3 --timeout 120
```

Choose `runs\haiku5p30` or `runs\codex_p30` as the source to review those candidates. The candidate input is copied `workspace/buggy.py`, not an edited `patched.py`. The validator runs the unchanged test against buggy, reference, and candidate by setting `MUT` to each module path. No repair agent is called.

Full outputs are written inside `$ValidationRun`, including `summary.csv`, `summary.json`, and per-case `result.json`. A subset produces `summary_issue_036.csv/json`. To evaluate only buggy/reference, use `baseline` instead of `validate`; exports are named `baseline_summary...`.

## Prepare a fresh manual repair workspace

The adapter prepares a new 30-case workspace without calling a model. This Python entry point avoids recopying the preserved `upstream/` files:

```powershell
$env:APR_NEW_RUN = Join-Path $AprRoot 'runs\manual_p30_01'
@'
import os
from pathlib import Path
import adapter

run = Path(os.environ["APR_NEW_RUN"])
if run.exists():
    raise SystemExit("Choose a new run directory.")
manifest = adapter.prepare(run, archive=None)
print("Prepared", manifest["count"], "cases:", run)
'@ | & $Python -B -X utf8 -
```

Preparation reads the existing sibling case directories and `test_validation/consolidated_data.json`, `consolidated_runs.json`, and optional `repair01/results.json` under `Part2_Create_test`. It selects cases using that evidence; it does not generate fixes. Edit only the fresh run's `tasks/<case>/workspace/buggy.py`, then call `adapter.py validate --run-dir` on that run. `task.json` includes evaluation-derived intent metadata, so this manual workflow does not reproduce the stricter Claude input policy.

The CLI equivalent is `adapter.py prepare --run-dir <fresh-path> --archive <zip-path>`, but that preparation step also recopies allowlisted ZIP sources into `upstream/`. The `archive=None` Python example preserves those historical files.

## Starting another paid Claude experiment

The retained Claude driver records this experiment with fixed model/folder specifications. It has no `--run-dir`, `--run-id`, or `--model` option. Even `--prepare-only` rewrites preparation artifacts. Do not invoke it against completed folders expecting a fresh experiment.

Before a new run, use a separate working copy or update specifications to fresh folders, separate comparison-report destinations, and a fresh broker queue. Review model IDs, recorded rates, original case/interpreter paths, and dependencies for the new experiment. A candidate deletion can still cause the historical driver to stop while saving its result; the one-time `claude_finish.py` recovery is not a generic solution for new runs.

The broker CLI requires `--credential-session`; it reads a key from a user message in that session file. It does not load `ANTHROPIC_API_KEY`, and the driver removes that variable from its environment. The previous key was removed, so the old credential-session workflow cannot restart this experiment. For a future run, provide a fresh key through a deliberate credential loader, such as a hidden prompt passed to `claude_api_broker.serve(queue, key)`. Keep the credential in the broker process; repair workers receive only the queue path.

After fresh output paths and credential loading are configured, the order is:

1. Prepare two fresh runs with `claude_p30.py --prepare-only`.
2. Start the network broker on a new writable queue and wait for `ready.json`.
3. Run `claude_p30.py --queue <new-queue> --workers 4 --repair-only` to finish generation before final tests.
4. Validate fresh candidates with unchanged tests, export comparisons to fresh report paths, and audit using the corresponding model/run mapping.
5. Stop the broker by creating `<new-queue>/stop`, retain its response evidence, and remove the temporary credential.

These are historical CLI interfaces; fresh-folder/authentication changes are prerequisites, not options already implemented. The driver also accepts `--cases <case>...` for subsets with `--repair-only`. A normal invocation without `--repair-only` runs final validation and writes comparison reports after generation.

## Agent flow and experiment limits

Claude flow: sanitized question + buggy program + pinned version + initial script error → `DefaultAgent` response → one monitored Bash action → script output/error feedback → next response → submission or limit → separate existing-test evaluation. Limits were 40 API calls, $1 per case checked before the next request, and 1,200 seconds per agent; a final response can exceed the cost limit. Shell-command timeout was 120 seconds.

Claude agents received no `fixed.py`, evaluation `test.py`, previous Codex patches, or validation-derived intent summaries. Final-test failures were not fed back into their repair loop. The earlier Codex run used a different orchestrated process, intent summaries, and test-feedback corrections; these scores do not isolate model performance under identical conditions.

All recorded runs used MCP disabled. Local pinned interpreters replaced the original Docker setup, and native Anthropic Messages replaced the ZIP's model transport. Monitored commands and Windows Job Objects do not provide OS filesystem/network isolation. Input exclusions, hashes, and visible-command audits do not prove absence of memorized training-data leakage or guard evasion. Tests can also miss intent requirements: the Codex `issue_009` repair passes while the original CSPLayout requirement remains unmet.

Original ZIP workflow and MCP/Docker instructions are preserved in `upstream/README_original.md`. Use those commands with the original project's complete installation; they do not describe the local no-MCP runs here.
