Existing case-specific tests are the evaluator. Each case was evaluated on one pinned Qiskit version: 0.25.3 for 6 cases, 0.46.3 for 12, and 2.5.0 for 12. These results cover those selections, not every case/version combination.

## Prepare a fresh manual repair workspace

The adapter prepares a new 30-case workspace without calling a model. This Python entry point avoids recopying the preserved `upstream/` files:

```powershell
$env:APR_NEW_RUN = Join-Path $AprRoot 'runs\manual_p30_01'
@'
import os
from pathlib import Path
import adapter

run = Path(os.environ["APR_NEW_RUN"])

    raise SystemExit("Choose a new run directory.")

'@ | & $Python -B -X utf8 -
```

Preparation reads the existing sibling case directories and `test_validation/consolidated_data.json`, `consolidated_runs.json`, and optional `repair01/results.json` under `Part2_Create_test`. It selects cases using that evidence; it does not generate fixes. Edit only the fresh run's `tasks/<case>/workspace/buggy.py`, then call `adapter.py validate --run-dir` on that run. `task.json` includes evaluation-derived intent metadata, so this manual workflow does not reproduce the stricter Claude input policy.

The CLI equivalent is `adapter.py prepare --run-dir <fresh-path> --archive <zip-path>`, but that preparation step also recopies allowlisted ZIP sources into `upstream/`. The `archive=None` Python example preserves those historical files.

## Starting another paid Claude experiment

The retained Claude driver records this experiment with fixed model/folder specifications. It has no `--run-dir`, `--run-id`, or `--model` option. Even `--prepare-only` rewrites preparation artifacts. Do not invoke it against completed folders expecting a fresh experiment.

Before a new run, use a separate working copy or update specifications to fresh folders, separate comparison-report destinations, and a fresh broker queue. Review model IDs, recorded rates, original case/interpreter paths, and dependencies for the new experiment. A candidate deletion can still cause the historical driver to stop while saving its result; the one-time `claude_finish.py` recovery is not a generic solution for new runs.

The broker CLI requires `--credential-session`; it reads a key from a user message in that session file. It does not load `ANTHROPIC_API_KEY`, and the driver removes that variable from its environment. The previous key was removed, so the old credential-session workflow cannot restart this experiment. For a future run, provide a fresh key through a deliberate credential loader, such as a hidden prompt passed to `claude_api_broker.serve(queue, key)`. Keep the credential in the broker process; repair workers receive only the queue path.

After fresh output paths and credential loading are configured, the order is:

1. Prepare two fresh runs with `claude_p30.py --prepare-only`.
2. Start the network broker on a new writable queue and wait for `ready.json`.
3. Run `claude_p30.py --queue <new-queue> --workers 4 --repair-only` to finish generation before final tests.
4. Validate fresh candidates with unchanged tests, export comparisons to fresh report paths, and audit using the corresponding model/run mapping.
5. Stop the broker by creating `<new-queue>/stop`, retain its response evidence, and remove the temporary credential.

These are historical CLI interfaces; fresh-folder/authentication changes are prerequisites, not options already implemented. The driver also accepts `--cases <case>...` for subsets with `--repair-only`. A normal invocation without `--repair-only` runs final validation and writes comparison reports after generation.

## GPT DefaultAgent experiment: files and execution

The GPT experiment uses `gpt-6-astra`, `gpt-6-luna`, and `gpt-6-sol` through the native OpenAI Responses API. It applies the Claude DefaultAgent protocol: the same 30 cases, initial buggy bytes, sanitized questions, Qiskit versions/interpreters, agent prompt templates, command guards, limits, and existing final tests. The runner copies frozen inputs from `runs/sonnet5.5p30/`; it does not copy Sonnet's generated repairs. `gpt-6.1-sol` is the earlier Codex experiment and is not a fourth run in this driver.

Reasoning effort and sampling use provider defaults. The request does not set a reasoning-effort or temperature override. The API transport changes to Responses function calling, with one `bash` action at a time, `parallel_tool_calls=false`, `max_output_tokens=8192`, and `store=false`. Encrypted reasoning items are retained in native responses and replayed with the conversation. The repair loop receives script execution output; final-test failures are not fed back to any GPT repair agent. MCP remains disabled.

## Agent flow and experiment limits

Claude flow: sanitized question + buggy program + pinned version + initial script error → `DefaultAgent` response → one monitored Bash action → script output/error feedback → next response → submission or limit → separate existing-test evaluation. Limits were 40 API calls, $1 per case checked before the next request, and 1,200 seconds per agent; a final response can exceed the cost limit. Shell-command timeout was 120 seconds.

Claude agents received no `fixed.py`, evaluation `test.py`, previous Codex patches, or validation-derived intent summaries. Final-test failures were not fed back into their repair loop. The earlier Codex run used a different orchestrated process, intent summaries, and test-feedback corrections; these scores do not isolate model performance under identical conditions.

All these workflows use MCP disabled. Local pinned interpreters replace the original Docker setup. The Claude runs use native Anthropic Messages, and the GPT runs use native OpenAI Responses in place of the ZIP's model transport. Monitored commands and Windows Job Objects do not provide OS filesystem/network isolation. Input exclusions, hashes, and visible-command audits do not prove absence of memorized training-data leakage or guard evasion. Tests can also miss intent requirements: the Codex `issue_009` repair passes while the original CSPLayout requirement remains unmet.
