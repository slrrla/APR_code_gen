The bug is that both attempts mix `qiskit.quantum_info` objects with the `opflow` API in ways it doesn't support.

1. **`Plus @ ~Plus` fails.** In opflow, `@` composes operators. A `StateFn` such as `Plus` can't be the first operand, so this raises `ValueError`. It doesn't build an outer product. The projector |+⟩⟨+| is the density matrix of `Plus`, so `Plus.to_density_matrix()` wrapped in a `MatrixOp` gives an opflow operator.
2. **`NumPyEigensolver` fails on a `quantum_info.Operator`.** In this version the solver expects an opflow `OperatorBase`, which has `to_spmatrix`. A raw `Operator` doesn't, hence the `AttributeError`. Wrapping it in `MatrixOp` converts it into an opflow operator. This is also the general way to move a `quantum_info` operator into opflow.

I haven't run the fixed code.

```python
import numpy as np
from qiskit.quantum_info import Statevector
# FIX: only Plus was imported -> also import MatrixOp, because it is needed to build opflow operators from matrices/Operators
from qiskit.opflow import Plus, MatrixOp
from qiskit.algorithms import NumPyEigensolver

# FIX: Plus @ ~Plus composes with a StateFn first, which is undefined -> build the projector from Plus's density matrix as a MatrixOp, because that is exactly |+><+|
proj = MatrixOp(Plus.to_density_matrix())

# FIX: a raw quantum_info Operator lacks to_spmatrix -> wrap it in MatrixOp, because NumPyEigensolver expects an opflow operator
plus = MatrixOp(Statevector([1/np.sqrt(2), 1/np.sqrt(2)]).to_operator())
solver = NumPyEigensolver()
spectrum = solver.compute_eigenvalues(plus)
```
